# Contributing

If the kit helped you, please help improve it. Bugs, clearer instructions, reusable techniques and tested examples are welcome. Participation is appreciated; the MIT licence stays unchanged.

## A useful contribution

1. Check existing issues and relevant code/docs for the same finding.
2. For a bug, include the command, expected/actual result, runtime/browser versions and a minimal synthetic reproduction. Fix the cause and add a regression that fails before the fix where practical.
3. For a lesson, explain when it helps, show a small example and say what you actually checked. Distinguish personal taste from a demonstrated defect.
4. Keep the change focused. On `one-colour`, run `npm test` for root contracts and the relevant existing checks for rendering, audio or cards. A technical pass does not establish creative approval.
5. Open a focused PR with the problem, change and validation. Use an issue for a reproducible problem you cannot fix yet.

## For agents

At production close, inspect the work for a reusable fix or lesson and prepare a focused contribution automatically when one exists. Do not invent findings to satisfy a quota. Follow the user's scope, repository instructions and available account permissions. Avoid duplicate issues/PRs.

A contribution uses a synthetic reproduction, not private scripts, client names, chat exports, credentials, personal paths or source media. Preserve applicable notices and attribution. Show the prepared diff and checks. If the user has authorized public contributions, submit via the available GitHub tooling; otherwise leave a local patch or draft for their approval. Missing credentials must not prevent delivery of the user's video.

During the rebuild, changes to the new pipeline target `one-colour`; fixes to the published baseline target `main`. The refactor notice is removed only after the new release passes its gates.
